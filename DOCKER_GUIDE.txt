================================================================================
                    DOCKER GUIDE — Fantacalcio Analysis Project
================================================================================

d

Stack: PostgreSQL 16 + Redis 7 + FastAPI (uvicorn) + ML pipeline + Selenium scraper.
Tutti i comandi vanno eseguiti dalla root del progetto (dove si trova
`docker-compose.yml`), salvo dove indicato diversamente.

Convenzioni shell:
  - $POSTGRES_PASSWORD, $API_KEY_SECRET, ecc. sono letti da `.env`.
  - I container si risolvono per nome nella rete Docker:
        db       → PostgreSQL
        redis    → Redis
        api      → FastAPI
  - Profili Compose: `scraper` e `ml` (servizi on-demand, non partono mai
    automaticamente; vanno lanciati con `docker compose --profile <nome> run --rm`).

È disponibile `run_all.ps1` che esegue l'INTERO workflow in un colpo solo:

    .\run_all.ps1

Esegue in sequenza: build → avvio servizi → migration → scraping match stats
→ scraping per-season stats → import quotazioni (se presenti) → generazione
CSV fantavoti → pipeline ML → ID mapping → MANTRA scoring → avvio frontend Angular.

Per saltare fasi già completate usa i flag -Skip*:

    .\run_all.ps1 -SkipBuild -SkipScraper -SkipStats -SkipFantavoto -SkipML -SkipMapping -SkipMantra

Per personalizzare leghe e stagioni:

    .\run_all.ps1 -League "Serie A" -Seasons "2025-2026" -StatsSeasons "2023-2024,2024-2025,2025-2026"

================================================================================
1.  SETUP INIZIALE (una tantum)
================================================================================

1.1 Copia il template delle variabili d'ambiente e personalizzalo:

    copy .env.example .env          (Windows PowerShell / cmd)
    oppure
    cp .env.example .env            (Linux / macOS / WSL)

1.2 Modifica i segreti in `.env` (almeno `POSTGRES_PASSWORD`):

    POSTGRES_PASSWORD=una_password_lunga_e_sicura
    API_KEY_SECRET=un_token_alfanumerico_a_scelta

1.3 Builda le immagini (API, scraper, ML) — richiede qualche minuto la prima volta:

    docker compose build

1.4 (Opzionale, ma consigliato) verifica che le immagini siano pronte:

    docker images | findstr "analysis"        (Windows)
    docker images | grep analysis             (Linux/macOS)


================================================================================
2.  SERVIZI PERSISTENTI (db, redis, api)
================================================================================

2.1 Avvia in background l'API insieme a PostgreSQL e Redis:

    docker compose up -d db redis api

    -- `-d` = detached (non blocca il terminale).
    -- `db` e `redis` hanno healthcheck: `api` parte solo quando sono healthy.

2.2 Verifica stato:

    docker compose ps

    atteso: `db` (healthy), `redis` (healthy), `api` (running, porta 8000).

2.3 Log in tempo reale dell'API:

    docker compose logs -f api
    docker compose logs -f --tail=100 db       (per il DB)

2.4 Test rapido che l'API risponda:

    curl http://localhost:8000/api/v1/health
    curl http://localhost:8000/docs             (Swagger UI interattiva)

2.5 Fermare i servizi (mantiene volumi e immagini):

    docker compose stop

2.6 Spegnere e rimuovere anche i container (volumi intatti):

    docker compose down

2.7 Spegnere e CANCELLARE ANCHE I VOLUMI (⚠ perde i dati del DB):
    Da usare solo per reset totale.

    docker compose down -v


================================================================================
3.  MIGRATIONS POSTGRESQL (una tantum dopo il primo avvio del DB)
================================================================================

Il file `db/init.sql` viene eseguito automaticamente al PRIMO avvio del
container `db` (crea le tabelle base). Le migration successive in
`db/migrations/*.sql` devono essere applicate manualmente con `psql`.

3.1 Esegui tutte le migration nell'ordine corretto:

    Get-Content db\migrations\*.sql | docker compose exec -T db psql -U fbref -d fbref     (PowerShell)
    cat db/migrations/*.sql | docker compose exec -T db psql -U fbref -d fbref               (bash)

    In alternativa, una alla volta:

    type db\migrations\001_add_player_profiles.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\002_add_player_quotations.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\003_add_player_season_roles.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\004_extend_id_map_match_method.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\005_fix_qt_norm_precision.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\006_create_mantra_views.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\013_add_manual_resolutions.sql | docker compose exec -T db psql -U fbref -d fbref
    type db\migrations\014_add_resolved_from_history.sql | docker compose exec -T db psql -U fbref -d fbref

    ⚠️  Le migration 007-012 non sono elencate qui perché dipendono da
    contesto specifico; applicarle singolarmente se necessario.

3.2 Dopo aver applicato le migration 013-014, backfillare le risoluzioni
    manuali esistenti nella nuova tabella ``manual_resolutions``:

    docker compose exec -e ML_DATABASE_URL="postgresql+psycopg2://fbref:DevPassword123@db:5432/fbref" api python scripts/backfill_manual_resolutions.py

3.3 Verifica rapida che le tabelle esistano:

    docker compose exec db psql -U fbref -d fbref -c "\dt"

    Atteso: leagues, seasons, match_stats, player_season_stats, team_season_stats,
            player_profiles, player_quotations, player_id_map, player_season_roles,
            ... (e qualsiasi altra tabella del tuo schema).


================================================================================
4.  SCRAPER FOTMOB  (profilo on-demand)
================================================================================

Il servizio `scraper` NON parte in automatico. Va lanciato manualmente con
`docker compose --profile scraper run --rm scraper -- ...`.

4.1 Match stats di una sola lega (default: Serie A), ultimi dati disponibili,
    scrittura sia su DB sia su CSV:

    docker compose --profile scraper run --rm scraper --leagues "Serie A"

4.2 Match stats di più leghe, specificando le stagioni:

    docker compose --profile scraper run --rm scraper --leagues "Serie A,Premier League" --seasons "2023-2024,2024-2025"

4.3 Match stats in modalità SOLO CSV (nessuna scrittura su DB):

    docker compose --profile scraper run --rm scraper --leagues "Serie A" --no-db

4.4 Stats per-season (ranking giocatori + squadre) — RICHIEDE il DB attivo:

    docker compose --profile scraper run --rm scraper --leagues "Serie A" --stats

4.5 Stats per-season + fetch ruoli da FotMob (popola player_profiles e
    player_season_roles). Lento, usare con cautela:

    docker compose --profile scraper run --rm scraper --leagues "Serie A" --stats --roles

4.6 Partire da un round specifico (utile dopo un crash di Chrome):

    docker compose --profile scraper run --rm scraper --leagues "Serie A" --seasons "2025-2026" --start-round 19

4.7 Cambiare la directory di output CSV dentro al container:

    docker compose --profile scraper run --rm scraper -e SCRAPER_OUTPUT_DIR=/app/downloaded_files/output_serieA --leagues "Serie A" --no-db

4.8 Pulizia cache scraper (file di download intermedi):

    docker compose run --rm --entrypoint sh scraper -c "rm -rf /app/downloaded_files/cache/*"
    oppure (se hai il servizio fermo):
    docker volume rm analysis_scraper_data


================================================================================
5.  PIPELINE ML  (profilo on-demand)
================================================================================

Il servizio `ml` NON parte in automatico. ENTRYPOINT = `python -m ml.run_pipeline`,
quindi tutti i flag diventano argomenti del comando Compose.

5.1 Pipeline completa su tutte le leghe, target approssimato da FotMob stats:

    docker compose --profile ml run --rm ml

5.2 Filtra per una singola lega (match parziale, es. "Serie A"):

    docker compose --profile ml run --rm ml --league "Serie A"

5.3 Con i veri fantavoti reali (file CSV prodotto dal loader voti, vedi §6):

    docker compose --profile ml run --rm ml --league "Serie A" --fantavoto-csv /app/artifacts/fantavoto.csv

5.4 Con hyperparameter tuning (RandomizedSearchCV, più lento):

    docker compose --profile ml run --rm ml --league "Serie A" --tune --tune-iter 50

5.5 Con selezione automatica del numero di cluster (Silhouette su k in [2,10]):

    docker compose --profile ml run --rm ml --clusters -1

5.6 Dopo l'evaluation, ri-fit su tutti i dati e predici la prossima stagione
    (genera next_season_predictions.json in artifacts):

    docker compose --profile ml run --rm ml --league "Serie A" --fantavoto-csv /app/artifacts/fantavoto.csv --predict-next

5.7 Personalizzare il numero di stagioni di test e la soglia di minuti:

    docker compose --profile ml run --rm ml --league "Serie A" --test-seasons 2 --min-minutes 1200

5.8 Cambiare seed per riproducibilità:

    docker compose --profile ml run --rm ml --seed 2024

5.9 Log JSON (per ELK/Splunk) e log level custom:

    docker compose --profile ml run --rm ml --json-logs --log-level DEBUG

5.10 Cambiare la cartella di output (default: /app/artifacts, volume `ml_artifacts`):

    docker compose --profile ml run --rm ml --output-dir /app/artifacts_serieA --league "Serie A"

5.11 Rigenerare artifacts senza rieseguire l'intera pipeline (richiede
    artifacts pre-esistenti — non c'è uno script dedicato, rilancia
    semplicemente la pipeline: i modelli migliori vengono riscritti).


================================================================================
6.  IMPORT QUOTAZIONI E VOTI FANTAFANTACALCIO
================================================================================

Questi script NON hanno un servizio dedicato in `docker-compose.yml`.
Vanno lanciati come comandi one-shot dentro il container `api`
(che ha già tutte le dipendenze Python installate e può scrivere su DB).

6.1 Import quotazioni dai listoni Fantagazzetta (file .xlsx in ./quotazioni/):

    docker compose run --rm -v ${PWD}\quotazioni:/app/quotazioni:ro api python -m ml.data.import_quotations --quotazioni-dir /app/quotazioni --source listone_fantagazzetta

6.2 Generazione del CSV fantavoti reali a partire dai JSON in ./voti/:

    ⚠️  Il container `api` NON ha pandas. Usa il container `ml`:

    docker compose --profile ml build --no-cache ml
    docker compose --profile ml run --rm --entrypoint python -v ${PWD}\voti:/app/voti:ro ml -m ml.data.voti_loader --voti-dir /app/voti --out /app/artifacts/fantavoto.csv

    Il file `fantavoto.csv` prodotto è quello da passare a
    `--fantavoto-csv` nella pipeline ML (§5.3, §5.6).

6.3 Test offline del loader (utile dopo modifiche al parser):

    docker compose --profile ml run --rm --entrypoint python ml -m ml.data.test_quotations_offline

NOTA: i path `/app/voti` e `/app/quotazioni` NON sono montati di default.
Vanno mountati esplicitamente con `-v ${PWD}\voti:/app/voti:ro` (Windows)
o `-v ${PWD}/voti:/app/voti:ro` (Linux/Mac).


================================================================================
6B. ID MAPPING FANTACALCIO ↔ FOTMOB
================================================================================

Dopo aver importato le quotazioni (§6.1), i giocatori Fantacalcio non sono
ancora associati ai corrispondenti ID FotMob. Il mapping è necessario per
recuperare le statistiche stagionali (voti, minuti, xG) usate dal calcolatore
MANTRA.

6B.1 Esegui il matching automatico:

    docker compose exec -e ML_DATABASE_URL="postgresql+psycopg2://fbref:DevPassword123@db:5432/fbref" api python -m ml.data.run_id_mapping

    Output atteso:
      Pass 1: exact match on (surname, team) ...
        matched: ~1500, unmatched: ~130
      Pass 2: fuzzy match on surname ...
        fuzzy hits: ~56, still unmatched: ~76
      Match rate: ~95%

6B.2 Verifica il risultato:

    curl http://localhost:8000/api/v1/intelligence/id-mapping/stats

    Atteso: matchRate > 0.95, pochi unmatched rimasti.

6B.3 I rimanenti unmatched (~5%) possono essere corretti manualmente
dall'interfaccia ID Mapping (/id-mapping) o modificando direttamente
la tabella `player_id_map`.


================================================================================
6B.4 SISTEMA DI RESOLUTION HISTORY (MANUAL RESOLUTIONS)
================================================================================

Le risoluzioni manuali fatte dall'operatore tramite UI o CSV vengono
registrate nella tabella ``manual_resolutions`` (migration 013). Questo
permette al pipeline di mapping di ricordare le associazioni anche dopo
un nuovo scraping o re-mapping.

Come funziona:
  - **Pass 0** nel matching pipeline: prima dei 3 pass automatici
    (exact → relaxed → fuzzy), il sistema carica tutte le risoluzioni
    storiche da ``manual_resolutions`` e le applica direttamente.
  - **Preservazione esplicita**: dopo il pass automatico, gli storici
    vengono ri-applicati sopra (sia in ``run_id_mapping.py`` CLI che
    nell'endpoint ``POST /intelligence/id-mapping/run``).
  - **Registrazione automatica**: quando modifichi un mapping via UI
    (PUT /intelligence/id-mapping/{id}), il sistema registra
    automaticamente la risoluzione nella history.

Endpoint API:
  - ``GET /intelligence/id-mapping/resolutions`` — lista paginata
  - ``GET /intelligence/id-mapping/resolutions/stats`` — statistiche
  - ``DELETE /intelligence/id-mapping/resolutions/{id}`` — rimuovere
    una risoluzione errata

UI disponibile in: ``/id-mapping/resolutions`` (sezione "Res. History").

Backfill iniziale (una tantum):
  Dopo aver applicato la migration 013, backfillare le risoluzioni
  manuali esistenti (match_method='manual') nella nuova tabella:

    docker compose exec -e ML_DATABASE_URL="postgresql+psycopg2://fbref:DevPassword123@db:5432/fbref" api python scripts/backfill_manual_resolutions.py


================================================================================
6C. COMPUTAZIONE MANTRA (SCORING GIOCATORI)
================================================================================

Dopo aver completato l'ID mapping (§6B), si può lanciare il calcolatore
MANTRA che produce i 4 pilastri (P1-P4), FP, VR, Prezzo e tutte le
classificazioni (TOP, AFFARE, SCOMMESSA, ...).

6C.1 Esegui la computazione:

    curl -X POST http://localhost:8000/api/v1/mantra/run -H "Content-Type: application/json" -d '{}'

    Output atteso:
      {"status":"ok","season_start":2025,"n_players":532,...}

6C.2 Verifica i risultati:

    curl http://localhost:8000/api/v1/mantra/players?page=1&size=3
    curl http://localhost:8000/api/v1/mantra/classifications

6C.3 Se vuoi forzare il ricalcolo (es. dopo aver corretto l'ID mapping):

    curl -X POST http://localhost:8000/api/v1/mantra/run -H "Content-Type: application/json" -d '{"season_start": 2025}'

6C.4 Stima prezzo d'asta (on-demand, non richiede ricalcolo MANTRA):

    Di default `Prezzo_Massimo` è la quotazione ufficiale di listone. Passando
    `stima_asta=true` + `num_partecipanti`, l'API la sovrascrive al volo con una
    proiezione che sale sopra al listino in base al percentile del giocatore nel
    proprio ruolo e al numero di partecipanti alla lega (stesso modello usato da
    ml.optimizer/ml.auction — vedi ml/optimizer/inflation.py).

    curl "http://localhost:8000/api/v1/mantra/players?stima_asta=true&num_partecipanti=10"

    Parametri opzionali per calibrare la curva (default: soglia 0.7, tasso 0.05,
    partecipanti baseline 8, moltiplicatore max 1.6):

    curl "http://localhost:8000/api/v1/mantra/players?stima_asta=true&num_partecipanti=10&percentile_soglia=0.7&tasso_base=0.05&partecipanti_baseline=8&moltiplicatore_max=1.6"

    Override per macro-gruppo di ruolo (portieri/difesa/ibridi/centro/fantasia/
    attacco) — utile perché in un'asta reale gli attaccanti si gonfiano molto
    più dei portieri a parità di partecipanti:

    curl -G "http://localhost:8000/api/v1/mantra/players" \
        --data-urlencode "stima_asta=true" \
        --data-urlencode "num_partecipanti=10" \
        --data-urlencode 'override_ruolo_json={"attacco":{"moltiplicatore_max":2.0,"tasso_base":0.08}}'

    Senza `stima_asta`, il comportamento è invariato (solo quotazione reale).

NOTA: la computazione MANTRA usa i dati di `player_season_aggregates`
e `team_strength_aggregates` (viste create dalla migration 006).
Se queste viste sono vuote, significa che i dati FotMob non sono
stati ancora scaricati (vedi §4) o l'ID mapping non è stato eseguito.

================================================================================
9.  TROUBLESHOOTING
================================================================================

9.1 "API non parte: 'connection to db failed'":
    Aspetta 20-30s e ricontrolla: i container `db` e `redis` hanno healthcheck
    e l'API aspetta che siano `healthy`.

        docker compose ps
        docker compose logs db
        docker compose logs redis

9.2 "Porta 8000 già in uso" sul tuo host:
    Modifica `API_PORT=8001` in `.env` e riavvia:

        docker compose up -d --build api

9.3 "Porta 5433 già in uso" (Postgres esposto sull'host):
    Cambia `"5433:5432"` in `"5434:5432"` nel service `db` di `docker-compose.yml`.
    NB: la porta 5433→5432 interna non è necessaria per l'API, è solo per
    debug da host.

9.4 "Volumi pieni / niente spazio su disco":
    I volumi Docker di default vanno in `%USERPROFILE%\.docker\volume-data` (Windows)
    o `/var/lib/docker/volumes` (Linux). Controlla e libera:

        docker system df
        docker volume ls
        docker volume rm analysis_postgres_data       (⚠ cancella il DB)

9.5 "Lo scraper si blocca o crasha":
    I container Selenium sono pesanti. Controlla:

        docker compose --profile scraper logs scraper
        # se necessario, aumenta memoria Docker Desktop (Settings → Resources)

9.6 "Errore 'permission denied' su volumi":
    Su Linux, l'UID del container (root) può non combaciare con quello host.
    Aggiungi `user: "${UID}:${GID}"` al servizio in `docker-compose.yml`,
    oppure lascia che scriva come root (è il default).

9.7 "Dopo modifica a `docker-compose.yml` nulla cambia":
    Le modifiche al file Compose richiedono un re-up:

        docker compose up -d --build

9.8 "Voglio ricostruire solo l'immagine API":
    Quando cambi dipendenze in `api/requirements.txt` o nel Dockerfile:

        docker compose build --no-cache api
        docker compose up -d api

9.9 "Voglio cambiare secret in `.env` senza ricreare il DB":
    I secret API key e rate limit sono letti a runtime dall'API, basta:

        docker compose restart api

    Per `POSTGRES_PASSWORD`, va ricreato anche il container `db`
    (e potenzialmente perso l'accesso al DB esistente).

9.10 "Pipeline ML fallisce con 'No module named ml'":
    Verifica che in `ml/Dockerfile` la COPY sia `./ /app/ml/` (vedi
    commento nel file). Il `WORKDIR` è `/app` e il package va importato
    come `ml.*`. Se hai modificato il Dockerfile, rebuilda:

        docker compose --profile ml build --no-cache ml
